FINAL PRODUCT GOAL
Build a Chrome Manifest V3 extension for normal YouTube VOD videos that already have captions:

  YouTube captions
    -> parse JSON3
    -> regroup/dedupe into sentence-sized units
    -> translate in ordered batches
    -> synthesize each translated sentence with TTS
    -> receive complete audio bytes
    -> Web Audio decodeAudioData()
    -> AudioBufferSourceNode
    -> schedule at original subtitle timestamp
    -> shared GainNode
    -> speaker

The intended behavior is Echoly subtitle-first:
- prepare a very small first wave
- resume the video quickly
- keep translation + TTS rendered ahead of the playhead
- when a subtitle timestamp arrives, its AudioBuffer should already be ready

LOCKED ECHOLY BEHAVIOR
Preserve unless a real browser test proves a defect and the user approves a change:
- translation batch size: 10 sentences
- lookahead: 30 seconds
- TTS render concurrency: 5 workers
- regroup gap: 1500 ms
- regroup max words: 15
- first wave: 2 forward sentences from current playhead
- pause YouTube only while preparing initial first wave
- audio sync:
    audioOffset = audioContext.currentTime - video.currentTime
    playAt = audioOffset + sentence.start
- schedule with AudioBufferSourceNode.start(playAt)
- seek: cancel scheduled sources -> recompute audioOffset -> schedule around new playhead
- original YouTube audio and dubbed voice remain separate
- dubbed voice uses one shared GainNode
- rolling renderer keeps translation/TTS ahead of playhead
- materially late cues are skipped instead of playing stale speech over the next cue

ONLY APPROVED ARCHITECTURAL CHANGE: PROVIDER ABSTRACTION

Translation core contract:
  translateBatch({
    lines,
    sourceLanguage,
    targetLanguage,
    signal
  }) -> Promise<string[]>

Rules:
- output MUST align 1:1 with input order
- core pipeline must not know Gemini/OpenAI/company-specific request bodies
- provider adapter owns URL, auth, model, request shape, response parsing
- model is config, never hard-coded in core
- preserve Echoly dubbing translation style: natural, concise, ordered, preserve names/brands/technical terms

TTS core contract:
  synthesize({
    text,
    voice,
    speed,
    signal
  }) -> Promise<{
    audio: ArrayBuffer,
    mimeType: string
  }>

Rules:
- core pipeline must not know MiniMax/VieNeu/Kyma/NovAI/company-specific schemas
- provider adapter owns URL, auth, model, voice mapping, request/response format
- use complete-file MP3/WAV in this phase
- NO streaming PCM / AudioWorklet
- shared audio layer runs decodeAudioData() and hands AudioBuffer to the Echoly-style scheduler
- changing provider/model later must not require edits to caption logic or scheduler

APPROVED FIX RELATIVE TO ECHOLY
Subtitle-first dub must respect YouTube pause/resume:
- pause: cancel pending scheduled dub sources and stop/suspend dub playback cleanly
- resume: resume AudioContext if needed, recompute audioOffset from video.currentTime, schedule around playhead again
- keep Echoly seek behavior
- do NOT replace scheduler architecture

TTS / AUDIO BEHAVIOR
For each translated sentence:
1. call configured TTS provider
2. receive complete audio response
3. convert to ArrayBuffer
4. decode with shared AudioContext
5. associate AudioBuffer with the sentence
6. schedule using Echoly timestamp model
7. connect:
   AudioBufferSourceNode -> shared GainNode -> audioContext.destination

Do NOT:
- use HTMLAudioElement as primary scheduler
- call audio.play() per subtitle
- replace timestamp scheduling with setTimeout/setInterval polling
