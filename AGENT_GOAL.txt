SUB-TO-VOICE-PRO — AGENT BUILD GOAL / NON-NEGOTIABLE BASELINE
================================================================

ROLE
You are the implementation agent for this project. Build the product inside:
  my-sub-to-voice

The sibling reference folder is:
  ../references

The Echoly source already placed under ../references is the architectural baseline and MUST be studied before writing product code.

FINAL PRODUCT GOAL
Build a Chrome Manifest V3 extension for YouTube VOD videos that have captions:
  YouTube captions
    -> regroup/dedupe into sentence-sized units
    -> translate in batches through a configurable Translation Provider
    -> synthesize each translated sentence through a configurable TTS Provider
    -> receive complete audio bytes
    -> Web Audio decodeAudioData()
    -> AudioBufferSourceNode
    -> schedule the dub at the original subtitle timestamp
    -> GainNode
    -> speaker

The intended user experience is Echoly's "subtitle-first" mode: prepare a small first wave, resume the video quickly, then keep translation/TTS rendered ahead of the playhead so dubbed audio is already buffered when its timestamp arrives.

LOCKED ECHOLY BEHAVIOR
Unless a browser test proves a defect and the user explicitly approves a change, preserve these subtitle-first tuning values and ideas:
- translation batch size: 10 sentences
- lookahead: 30 seconds
- TTS render concurrency: 5 workers
- regroup sentence boundary gap: 1500 ms
- regroup maximum words: 15
- first wave: 2 forward sentences from the current playhead
- pause the YouTube VOD only while preparing the initial first wave
- audio sync model:
    audioOffset = audioContext.currentTime - video.currentTime
    playAt = audioOffset + sentence.start
- schedule with AudioBufferSourceNode.start(playAt)
- seek: cancel scheduled dub sources, recompute audioOffset, schedule around the new playhead
- original YouTube audio and dubbed voice are separate audio paths
- dubbed voice goes through a GainNode
- rolling renderer keeps translation/TTS prepared ahead of the playhead
- if a scheduled cue is already materially late, skip it rather than blasting stale speech over the next cue

ONLY APPROVED ARCHITECTURAL CHANGE: PROVIDER ABSTRACTION
Echoly currently binds translation/TTS details too closely to specific providers/models. This project MUST decouple both.

Translation core contract:
  translateBatch({
    lines,
    sourceLanguage,
    targetLanguage,
    signal
  }) -> Promise<string[]>

Rules:
- output array MUST align 1:1 with input lines
- core pipeline must not know "Gemini", "OpenAI", "Kyma", or any company-specific request body
- provider adapter owns URL, auth headers, model name, request shape, and response parsing
- model name is configuration, never hard-coded in the core pipeline
- keep the Echoly dubbing translation behavior: concise, natural translation intended to fit the source speaking window; strict ordered output

TTS core contract:
  synthesize({
    text,
    voice,
    speed,
    signal
  }) -> Promise<{
    audio: ArrayBuffer,
    mimeType: string
  }>

Rules:
- core pipeline must not know "MiniMax", "VieNeu", "Kyma", "Novita", or any company-specific schema
- provider adapter owns URL, auth, model, voice field mapping, request shape, and response parsing
- request complete-file audio for this phase (MP3 or WAV preferred)
- NO streaming PCM/AudioWorklet architecture in this phase
- the shared audio layer receives bytes, calls decodeAudioData(), stores AudioBuffer, and hands it to the unchanged scheduler
- adding provider C/D later must not require edits to caption logic, dubbing pipeline, decoder, or scheduler

INITIAL PROVIDER STRATEGY
Implement a small provider registry, not provider checks scattered across the app.
At minimum support:
1. an OpenAI-compatible translation adapter with configurable base URL + model + API key where possible
2. an OpenAI-compatible TTS adapter with configurable base URL + model + API key + voice where possible
3. a provider-specific adapter only when a provider's schema actually differs
4. VieNeu TTS support as a first-class selectable provider if the user's v4 API contract requires fields that differ from the generic adapter

Do not create a backend/proxy server unless the user explicitly asks for one. The extension should call configured provider APIs directly, following Chrome MV3 permissions rules.

APPROVED FIX RELATIVE TO ECHOLY
Subtitle-first dub audio must truly respect YouTube pause/resume:
- on pause: stop/cancel pending scheduled dub sources and suspend or otherwise stop dub playback cleanly
- on resume: resume the AudioContext if needed, recompute audioOffset from the current video.currentTime, then schedule around the playhead again
- keep Echoly seek behavior
This fix must not be turned into a new scheduler architecture.

IF A VIDEO HAS NO CAPTIONS
Stop cleanly and show a clear message such as:
  "This phase requires a YouTube caption track."

TRANSLATION BEHAVIOR
Keep Echoly's sentence regrouping and ordered batch translation semantics.
The translation prompt should preserve:
- natural target-language dubbing
- concise wording
- names/brands/technical terms
- same output order and same item count as input
Do not send one network request per tiny YouTube ASR cue if regrouping can produce useful sentence units.

TTS / AUDIO BEHAVIOR
For each translated sentence:
1. call configured TTS provider
2. receive the complete audio response
3. convert response to ArrayBuffer
4. decode with the shared AudioContext
5. store the resulting AudioBuffer on/against the sentence
6. schedule it with Echoly's timestamp model
7. connect source -> shared output GainNode -> audioContext.destination

Do not use HTMLAudioElement as the primary subtitle-first scheduler.
Do not call audio.play() per subtitle.
Do not replace timestamp scheduling with setTimeout/setInterval polling.

BROWSER TEST REQUIREMENT
This is not complete because static checks pass. The agent must test it in Chrome as an unpacked extension.

For every browser test:
1. reload the unpacked extension
2. open/reload a normal YouTube VOD with a known caption track
3. configure provider credentials through the extension UI; do not paste secrets into source
4. start the dub
5. verify caption fetch succeeds
6. verify translated lines remain ordered
7. verify first wave is audible at the expected subtitle timestamps
8. verify rolling lookahead continues generating audio
9. verify original and dub volume controls work
10. pause YouTube and verify dub stops
11. resume and verify dub resynchronizes
12. seek forward and backward and verify stale scheduled speech is cancelled and the new region is scheduled
13. stop and verify requests/audio/session resources are cleaned up
14. inspect DevTools for uncaught errors

If credentials are unavailable, complete all non-live tests and report the live-provider E2E as the exact remaining blocker. Never fake a successful browser test.
