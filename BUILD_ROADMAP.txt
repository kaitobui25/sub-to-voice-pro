SUB-TO-VOICE-PRO — BUILD ROADMAP / PHASE PLAN
================================================

TARGET
Build the smallest reliable product that preserves Echoly's subtitle-first YouTube dubbing behavior while removing unused modes and decoupling Translation and TTS providers/models.

IMPORTANT
AGENT_GOAL.txt is the binding design contract.
This roadmap defines execution order.
If this roadmap and AGENT_GOAL.txt ever appear to conflict, follow AGENT_GOAL.txt.

GENERAL BUILD RULE
Do not jump directly to a full implementation.
Finish each phase, run its checks, commit it, then continue.
If a phase gate fails, fix it before moving on. Do not pile later features on top of a broken subtitle/audio path.

GIT RULES
- Work only in my-sub-to-voice product source.
- Never modify ../references.
- Commit after every completed phase.
- Use small descriptive commits.
- Push only tested phase commits.
- Never force-push.
- Never commit API keys, cookies, bearer tokens, generated audio, or local Chrome profile data.

Suggested commit sequence:
  docs/reference-audit
  feat/mv3-subtitle-baseline
  feat/translation-provider-layer
  feat/tts-provider-layer
  feat/web-audio-dub-scheduler
  feat/session-controls
  feat/provider-settings-ui
  test/browser-e2e
  fix/hardening
  chore/release-ready

PHASE 0 — REFERENCE AUDIT / FREEZE THE BASELINE
----------------------------------------------------------------

Goal:
Understand exactly how local Echoly subtitle-first works before product code is written.

Tasks:
1. Inspect ../references and locate the local Echoly copy.
2. Read AGENT_GOAL.txt fully.
3. Read Echoly manifest.json, background.js, and the relevant content.js functions listed in AGENT_GOAL.txt.
4. Trace one complete captioned-YouTube path:
     Start
       -> fetch caption URL
       -> JSON3 parse
       -> regroup/dedupe
       -> translate batch
       -> TTS
       -> decode
       -> first-wave schedule
       -> video resumes
       -> rolling lookahead
       -> pause/seek/stop cleanup
5. Record a short implementation mapping in project notes or commit message:
   - source Echoly function
   - destination product module/function
   - whether behavior is copied unchanged or intentionally adapted
6. Confirm the locked constants:
   batch=10
   lookahead=30s
   TTS concurrency=5
   regroup gap=1500ms
   max words=15
   first wave=2

Gate:
Agent can explain the actual Echoly subtitle-first data/audio flow from code, not from README assumptions.

Do not implement yet if this gate is not satisfied.

PHASE 2 — TRANSLATION PROVIDER ABSTRACTION
----------------------------------------------------------------

Goal:
Preserve Echoly translation behavior without hard-coding Gemini or any provider/model in the core pipeline.

Tasks:
1. Implement the Translation Provider interface from AGENT_GOAL.txt.
2. Implement TranslationManager.
3. Implement provider registry/config.
4. Implement at least one configurable OpenAI-compatible translation adapter.
5. Provider adapter owns:
   - base URL
   - API key/auth
   - model name
   - request body
   - response parsing
6. Core pipeline owns:
   - batching
   - subtitle order
   - target language
   - cancellation/session validity
7. Port Echoly's concise dubbing translation instruction:
   - natural target language
   - concise phrasing
   - preserve names/brands/technical terms
   - exactly same line count and order
8. Preserve batch size=10.
9. Add response validation:
   - if returned item count differs, handle deterministically
   - never silently reorder lines
10. Model name must come from settings/config.

Unit/static tests:
- fake provider returning deterministic text
- 1, 10, >10 sentence batching
- malformed provider output
- abort signal
- ordering preserved

Browser gate:
With a real configured translation API, show translated lines for a real captioned YouTube VOD.
No TTS required yet.

Commit:
  feat: add configurable translation provider layer

----------------------------------------------------------------
PHASE 3 — TTS PROVIDER ABSTRACTION
----------------------------------------------------------------

Goal:
Replace Echoly's MiniMax-specific dependency with a provider-neutral TTS layer while preserving whole-file audio rendering.

Tasks:
1. Implement TTS Provider interface from AGENT_GOAL.txt.
2. Implement TTSManager.
3. Implement configurable OpenAI-compatible TTS adapter.
4. Implement VieNeu adapter only if the user's v4 API differs from the generic adapter.
5. Provider owns:
   - endpoint/base URL
   - API key/auth
   - model
   - voice/voice field mapping
   - speed request field if supported
   - output format request
6. Core requests full MP3 or WAV response.
7. Return:
     {audio: ArrayBuffer, mimeType}
8. No provider-specific fields may leak into the audio scheduler.
9. Never hard-code MiniMax or VieNeu model names in shared pipeline code.

Tests:
- fake provider returns a known small audio fixture or mocked ArrayBuffer
- API error surfaces clearly
- abort cancels request
- provider switch changes only selected adapter/config
- no credentials in repository

Commit:
  feat: add configurable TTS provider layer

PHASE 4 — PORT ECHOLY AUDIO DECODER + SUBTITLE-FIRST SCHEDULER
----------------------------------------------------------------

Goal:
Make translated TTS audio play using Echoly's exact Web Audio timing model.

Tasks:
1. Create one shared AudioContext per active subtitle-first session.
2. Create shared output GainNode.
3. Decode complete provider audio with decodeAudioData().
4. Store AudioBuffer associated with each sentence.
5. Port renderWaveTTS behavior:
   - concurrency = 5
   - skip already-buffered sentences
   - a failed sentence may be silent, but must not crash the whole session
   - surface an understandable failure count/status instead of silent failure
6. Port scheduleWindow:
     at = audioOffset + sentence.start
     AudioBufferSourceNode.start(at)
7. Preserve the Echoly late-cue skip behavior.
8. Preserve first-wave=2.
9. Preserve lookahead=30 seconds.
10. Preserve runRollingRenderer concept.
11. Keep audio path:
     AudioBufferSourceNode -> GainNode -> destination
12. Do not replace scheduling with HTMLAudioElement or setTimeout-based playback.

Deterministic tests:
- mock video.currentTime + mocked clock calculations
- playAt math
- late cue skip
- scheduled source cancellation
- repeated schedule does not intentionally duplicate an already-scheduled source

Browser gate:
With translation + TTS credentials:
- click Start mid-video
- first two sentences prepare
- video resumes
- first dubbed sentence is heard near the intended subtitle timestamp
- rolling lookahead continues

Commit:
  feat: port Echoly subtitle-first Web Audio scheduler

----------------------------------------------------------------
PHASE 5 — SESSION CONTROLS / PAUSE / RESUME / SEEK / STOP
----------------------------------------------------------------

Goal:
Keep Echoly's session lifecycle but apply the one approved pause/resume synchronization fix.

Tasks:
1. Maintain a single active session.
2. Use AbortController for provider requests.
3. Use a session/token/stale-callback guard so stopped/restarted sessions cannot mutate current state.
4. Seek:
   - cancel pending AudioBufferSourceNodes
   - recompute audioOffset
   - schedule around new playhead
5. Pause APPROVED FIX:
   - cancel pending dub sources
   - stop dubbed playback cleanly; suspend AudioContext if appropriate
6. Resume APPROVED FIX:
   - resume AudioContext if needed
   - recompute audioOffset
   - schedule around current playhead
7. Stop:
   - abort translation/TTS requests
   - cancel sources
   - disconnect nodes
   - close AudioContext
   - restore original YouTube volume
   - clear UI/session state
8. Video ended -> clean stop.
9. YouTube SPA video change -> old session must not bleed into new video.
10. Do not implement playbackRate support.

Browser gate:
- pause for 5+ seconds: no dub continues speaking
- resume: voice re-syncs to current video
- seek forward: old voice stops; new region begins when buffered
- seek backward: already-buffered region can be reused/rescheduled where valid
- Stop produces silence immediately and no orphan network activity

PHASE 7 — FULL BROWSER E2E
----------------------------------------------------------------

Goal:
Prove the actual product works in Chrome, not only in mocks/static tests.

Preparation:
- do not put keys in source
- configure keys through popup/local extension settings
- use a normal non-live YouTube VOD with a reliable caption track
- test at 1x playback speed

E2E scenario A: start from beginning
1. reload extension
2. reload YouTube
3. Start
4. captions fetched
5. sentences regrouped correctly
6. translation returns ordered target lines
7. first 2 TTS buffers render
8. video resumes
9. dubbed voice plays on expected timestamps
10. next 30s stays buffered ahead
11. original/dub volume controls work

E2E scenario B: start mid-video
- seek manually to a middle section before Start
- first wave must begin from the current playhead, not sentence index 0

E2E scenario C: pause/resume
- pause long enough that pre-scheduled audio would have fired in the old Echoly bug
- confirm no dub leaks while paused
- resume and confirm resync

E2E scenario D: seek
- seek +60s
- no stale old-region voice
- new region translates/renders/schedules
- seek backward
- scheduler behaves correctly again

E2E scenario E: failure paths
- bad translation key
- bad TTS key
- provider 4xx/5xx
- no captions
- Stop during in-flight translation/TTS
Each failure must be visible and must not leave the extension stuck in "Translating".

Record:
- YouTube test URL/video id
- browser/Chrome version
- providers/models used, but NOT keys
- startup time observed
- obvious sync issues
- console errors, if any

PHASE 8 — HARDENING WITHOUT ARCHITECTURE CHANGES
----------------------------------------------------------------

Goal:
Fix concrete issues discovered in E2E while keeping the locked pipeline intact.

Allowed hardening:
- clean stale callbacks
- remove ended source references to avoid memory growth
- better retry/error messages where safe
- cache already rendered AudioBuffers for seek-back
- avoid duplicate scheduling
- clean YouTube SPA navigation
- tighten host/optional permissions
- improve AbortController coverage
- correct provider response parsing
- clean UI state
- preserve original volume correctly

Not allowed:
- replace Web Audio scheduler
- add Realtime
- add audio capture fallback
- add live stream support
- add playback-rate scheduling
- replace sentence regrouping strategy wholesale
- introduce streaming TTS
- add server/proxy
without a new user decision.

Regression browser gate:
Repeat Phase 7 after every scheduler/session fix.

----------------------------------------------------------------
FINAL PRINCIPLE
----------------------------------------------------------------

This product is not a greenfield audio experiment.

It is:
  Echoly subtitle-first
  MINUS:
    Realtime/WebRTC
    no-caption audio capture fallback
    live streams
    playback-rate work
  PLUS:
    provider/model abstraction for Translation
    provider/model abstraction for TTS
    VieNeu-capable TTS adapter
    correct pause/resume dub synchronization
    clearer failure handling

When a choice is unclear, preserve Echoly's existing subtitle-first translation and playback behavior and make the smallest change needed to satisfy the additions above.
